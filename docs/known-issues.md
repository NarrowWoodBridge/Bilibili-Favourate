# 已知问题与安全提示

## Python 版本兼容

当前 `scripts/webapi.py` 只在 `TYPE_CHECKING` 为真时导入 `User`，但函数注解直接写成 `User`。Python 3.13 及更早版本默认会在定义函数时求值该注解，因此导入模块可能触发：

```text
NameError: name 'User' is not defined
```

Python 3.14 的延迟注解求值可避免导入时立即触发该错误。为了兼容更早版本，后续重构仍应使用字符串注解、`from __future__ import annotations`，或调整模块依赖。本文只记录现状，没有修改业务代码。

## 凭据安全

- `功能性文件/cookies.md` 包含登录 Cookie，必须保持在 Git 之外。
- `cookies.example.md` 只能保留占位符，不能复制真实浏览器值后再提交。
- 控制台日志不应输出请求头、Cookie 或完整 API 请求上下文。
- Cookie 失效时，当前代码可能以 `KeyError` 等间接异常失败，而不是给出明确的登录提示。

如果真实 Cookie 曾经提交到版本库，仅删除当前文件并不够；还应立即在 Bilibili 退出相关会话或更新凭据，并按需要清理 Git 历史。

## 网络与 API

- HTTP 请求没有超时、重试、`raise_for_status()` 或统一 JSON 错误处理。
- 收藏夹数量恰好为 20 的倍数时会额外请求一个空页。
- 代码假设响应始终包含 `data`、`list`、`medias` 等字段；登录过期、限流、404 或接口变化可能直接抛出异常。
- `User` 构造期间就会访问网络；`main()` 内还会再次请求一次收藏夹列表，且该返回值当前未使用。
- `infoDict.json` 没有过期机制，已有 `bvid` 的元数据和合集列表不会自动刷新。

## 导入与执行副作用

- `scripts/User.py` 在模块顶层读取配置、Cookie 并构造 `User`。
- `User.__post_init__()` 会立即请求收藏夹和其中的全部视频。
- `scripts/main.py` 在模块末尾直接调用 `main()`。

因此当前脚本不能安全地作为库导入，也不适合在测试中只导入单个业务函数。

## 文件匹配与命名

- 文件存在性主要按标题匹配，不按 `bvid` 唯一匹配；同名视频可能命中错误文件。
- 多 P 视频的所有分 P 共用一个 `bvid`，仅靠 BV 号也不足以区分分 P 笔记。
- 合集按清洗后的标题合并，不按合集 ID；同名合集可能被合并到错误目录。
- 收藏夹名称只保留基本汉字，英文、数字和符号会被删除，且可能产生空名称或重名。
- `xreplace()` 没有处理反斜杠、星号、尾随句点、Windows 保留设备名等全部非法文件名情况。
- `xexists()` 返回递归遍历中的第一个匹配项，重复标题时行为依赖文件系统遍历顺序。

## Markdown 与数据保留

- 启动扫描假设每份 `.md` 都有 `---` 包围的 YAML；普通说明文档放进输出目录可能导致解析失败。
- 合集目录必须按顺序包含 `# 视频` 和 `# 笔记`，否则更新时不能正常解包。
- 分段匹配使用“行内包含”而非整行相等，正文中出现相同文字也可能被误判为标题。
- 完整合集移动旧笔记后会重新生成 YAML，只保留脚本识别的有限字段；自定义 YAML 属性可能丢失。
- 合集更新只新增或转换链接，不会清理远端已删除的视频条目。
- 写入、移动和重命名没有事务或回滚机制；中途失败可能留下部分更新结果。

在这些问题修复前，首次切换合集为“完整同步”或处理大量既有笔记前，应备份 `B站视频/`。
